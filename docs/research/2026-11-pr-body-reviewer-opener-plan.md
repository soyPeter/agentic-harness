## Evidence and baseline

- **Source (primary):** Simon Willison, ["Hide your slop PR descriptions behind details/summary"](https://simonwillison.net/2026/Nov/9/details-summary/), 9 Nov 2026. He opens agent-written PRs with a short human-approved paragraph (sometimes a screenshot), then folds the full agent-written description in a GitHub `<details>` block whose `<summary>` names the model and effort level. His stated reason: accurate, comprehensive agent descriptions still read as "too long to read", so reviewers skip them. This is a practitioner's account, not a study.
- **Documented harness behavior (docs read, code not audited):** the deliverer opens or updates the PR "with each task's receipt" and the reviews' follow-ups, applies suggested `risk:*`/`class:*` labels, never edits files and never merges. The receipt lists Changed, Verified, **Not verified**, Sandbox, Decisions, Risks, **Approval needed** and Suggested labels. Read on 2026-11-09 at HEAD `2abcf53ad7a7b0ce418e43730751948b2863d5b4`.
- **Not checked:** how the PR body is actually assembled in code, its current length on real PRs, multi-task PR layout, Orca coordinator output, GitHub rendering of nested folds. Whether reviewers skip receipt content today is a **hypothesis**.

## Problem

The receipt is the harness's evidence for the human merge gate. If the PR body is a long wall of agent text, the items that need a human (Not verified, Approval needed, open escalations, elevated risk) can be missed — the opposite of the receipt's purpose. Naively copying the "fold everything" pattern would make that worse by hiding exactly those items.

## Options

| Option | Benefit | Cost / risk |
|---|---|---|
| A. Keep the current body | No change; nothing hidden | Reviewer fatigue on long multi-task PRs remains (unmeasured) |
| B. Fold the whole agent description (Willison as-is) | Shortest page | **Hides Not verified / Approval needed** — weakens the merge gate; rejected |
| C. Reviewer-first layout: short opener + always-visible "needs you" block + folded full receipt | Keeps every gate-relevant item visible while cutting length | Template work; the opener is agent-drafted unless a person edits it, so it must be labelled honestly |

**Proposed: C.** A remains the fallback if C doesn't measurably help.

## Proposed body layout (C)

1. **Opener (1–3 sentences):** what the PR is for and why a reviewer should care. Drafted by the deliverer from the spec's intent; marked `_Agent-drafted opener; not yet edited by a person._` The harness never claims human authorship. A person may replace it; the deliverer must not overwrite a body section a person has edited (detection approach to be decided in WP1).
2. **Needs you (never folded):** Not verified items, Approval needed (non-Accepted ADRs, open escalations), the `risk:*` label with its reason, and the Sandbox line when the judge pass was not isolated or not recorded. If empty, say "Nothing flagged by the receipt" — not "verified" or "safe".
3. **Folded detail:** `<details><summary>Change receipt — task <id> (generated by harness <version>; agent <role/model if recorded>)</summary>` containing the full receipt unchanged. Name the model only if the run records it; never guess.
4. Review follow-ups stay as today (placement decided in WP1).

## Risks and rollback

- **Hidden evidence:** mitigated by the WP2 "outside the fold" tests; this is the acceptance criterion that matters most.
- **False human signal:** the opener is labelled agent-drafted; nothing upgrades that label automatically.
- **Overwriting human edits:** deliverer must preserve edited sections (WP1 decides how) or leave the body alone.
- **Rendering:** GitHub supports `<details>`/`<summary>` in Markdown (per the source); other forges/viewers may not — the receipt must stay readable as plain text.
- **Rollback:** template change only; revert the commit to restore today's body. No stored data changes.
