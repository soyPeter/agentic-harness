# Agent-SDLC landscape: compliance/traceability and agent sandboxes

**Date:** 2026-11-06
**Status:** Research only. No decision recorded, no code changed. Companion to [ADR-001](../adr/ADR-001-thin-mode-plugin.md) and [ADR-002](../adr/ADR-002-change-class-ladder.md).
**Question:** what in this space should `agentic-harness` learn from, integrate with, or ignore?
**Starting points:** Ketryx (AI-native compliance / QMS), Daytona (sandboxes for AI-generated code). Added during research: HumanLayer (`humanlayer.dev`) and Modal (`modal.com`).

## Method and caveats

- All URLs were accessed **2026-11-06** unless an inline source date is given. Primary sources (vendor docs, pricing pages, GitHub repos, `LICENSE` files, standards bodies, `api.github.com`) were preferred; third-party aggregators are labelled and de-rated.
- The `websearch` tool was unavailable for the whole research session (every call returned `Web search cancelled`). Findings come from `webfetch` against primary URLs plus DuckDuckGo/Bing/Yahoo HTML result pages as a search substitute. Search snippets are secondary. This limits landscape completeness; several items are therefore marked **UNVERIFIED** rather than guessed.
- Inline markers: **`[STALE]`** = source materially older than 2026-11-06 or superseded; **`[UNVERIFIED]`** = could not confirm from a primary source. A consolidated register is at the end.
- Vendor claims (funding, scale, compliance) are reported as claims. "No PCI-DSS attestation found" means exactly that on the pages fetched, not a statement about the vendor's actual certification.
- Prices are those shown on the cited page on the access date; most enterprise tiers are quote-only.

## Executive summary — ranked recommendations

1. **Define a `SandboxBackend` interface and evidence fields in `harness.py receipt` before touching any vendor.** Keep the local `payload/owned/.devcontainer/harness-agent/` as the default backend **and** the `harness-verify` CI-floor backend (the base-branch verifier must not depend on a vendor SDK, image or control plane). Highest leverage, no vendor, unblocks every other item. Also harden what already exists: move the egress allowlist to an external proxy so the guest no longer needs `NET_ADMIN`/`NET_RAW`, pin the image by digest, and record `backend`, `isolation_class`, `image_digest`, `allowlist_hash`, `region`, `control_plane` and `credential_mode` in the receipt. **~1–2 engineer-weeks.**
2. **Build one vendor-neutral evidence exporter from `harness.py receipt`, not a QMS integration.** Emit **ReqIF 1.2 XML** (OMG standard, stdlib `xml.etree`) and **Sphinx-Needs `needs.json` format 1** as optional, derived, git-committed artifacts; render an HTML traceability matrix in CI for PRs / Linear comments. `backbone/`, git and Linear stay the system of record; the export is one-way, non-authoritative, has no SaaS egress and adds no runtime dependency. This is the cheapest way to serve a regulated customer's requirements-to-test traceability demand without buying a vendor. **~1–2 engineer-weeks** (ReqIF) + **~3–5 days** (`needs.json`).
3. **Sign verdicts in CI instead of buying a compliance platform.** Emit an in-toto `Statement` whose subject is the commit/code digest with a custom verdict predicate (or a SLSA v1.2 Verification Summary Attestation-style envelope), signed with `cosign` in the `harness-verify` workflow. This makes the "AC → passing test → fingerprinted verdict → receipt" chain independently verifiable and does not change the stdlib-only Python core. Use a custom `predicateType`; **do not fabricate SLSA levels**. Prefer self-managed keys/KMS over keyless signing (public transparency logs hold signer PII). **~1–2 engineer-weeks.**
4. **Treat Daytona as learn-from / narrow opt-in, not a self-hostable dependency.** Its OSS repo was **archived 2026-10-03** and core development moved to a private codebase in June 2026; the only self-hostable artefact is a frozen, unpatched **AGPL-3.0** `v0.190.0`. If a cloud sandbox backend is later needed, evaluate **E2B** (Apache-2.0 Firecracker stack, BYOC / single-node Embed, best exit path) for residency-sensitive work and **Coder** (control plane in our own infra) for full self-hosting — both behind the §1 interface. **Ignore Modal / Codespaces / Northflank for the `triple` pilot**: Modal and Codespaces are SaaS-only with no self-host, and Northflank has an unresolved control-plane secret compromise (RCA pending 2026-11-06). **~2–4 engineer-weeks per adapter**, plus platform ops.
5. **Keep policy gates in stdlib Python; learn from OPA and HumanLayer; defer observability.** OPA/Rego has an explicit "Agent Tool Calling" PEP/PDP pattern and decision logs worth copying, but adding a Go/Rust binary breaks the stdlib-only Python 3.8 design — ship at most an opt-in, fail-closed, checksum-pinned adapter. HumanLayer's human review of plan/design artifacts is a good contrast case, not a replacement for our git/spec approval. If an OTel exporter is ever built, emit generic OTLP + `harness.*` attributes (ids/hashes/verdicts only) to a **self-hosted** sink; never send spec/AC bodies or tool arguments to a SaaS for the Disputes/PCI-DSS pilot. **~1 engineer-week** for an OPA prototype; **~4–7 days** for an exporter.

**Cross-cutting finding:** no tool in either space publishes a PCI-DSS attestation on the pages reviewed. That matches the repo's own position (`catalog/triple/README.md`: the `harness-agent` devcontainer is explicitly **not** a PCI attestation). For the supervised pilot, the correct control is to keep cardholder data out of the sandbox by allowlist + scoped credentials + human merge, and make that exclusion auditable in the receipt — not to buy a "PCI-compliant" product. Every SaaS integration, even on non-PCI surfaces, adds a subprocessor and a new data flow requiring review.

## Where this touches the harness

Five seams, derived from README.md and the two ADRs:

| Seam | Harness mechanism today | What the landscape offers |
|---|---|---|
| Evidence export | `harness.py receipt <id>` (what changed, each AC with tests, what is **not** verified, decisions/risks), posted into PRs and Linear (`linear receipt`) | ReqIF / `needs.json` / `.sdoc` exporters; QMS build APIs; signed attestations |
| Sandbox backend | `payload/owned/.devcontainer/harness-agent/` — one container per unattended `harness.py run`, `init-firewall.sh` outbound allowlist, no host credentials, `--dangerously-skip-permissions` | microVM / gVisor isolation, host-side egress policy, secrets at egress, snapshots/fork, per-second metering, self-host control planes |
| Policy gate | `backbone/tools.conf`, `routing.conf`, guardrails, Change-Class ladder (`docs` / `refactor` / `feature` / `schema`), `approve`, escalation | Rego/Cedar declarative policy, decision logs, approval state machines |
| Observability | `harness.py report` (event log), `harness.py trace <id>` (context/skills loaded, files edited, hooks refused, test runs, verdicts) | OTLP sinks, GenAI span conventions |
| Integrity | verdicts fingerprinted to code in `backbone/.verdicts/`, `harness-verify` with the base branch's verifier | in-toto / SLSA VSA / cosign signed attestations |

The harness's distinguishing property is that verdicts are **fingerprinted to code** and re-derived by a base-branch verifier. None of the tools below models that; almost all model *process state* (items, reviews, signatures) or *LLM calls*. Any integration must keep git as the source of truth.

### Isolation / cold-start / egress comparison (Space 3 + 4)

| | plain Docker container (current devcontainer) | gVisor | Firecracker / KVM microVM |
|---|---|---|---|
| Boundary | namespaces + cgroups + reduced caps + seccomp on a **shared host kernel** | userspace application kernel (`runsc`); syscalls not passed to host kernel; not a VM | own guest kernel, hardware virtualization, 5 emulated devices, `jailer`; <125 ms boot, <5 MiB overhead |
| Escape consequence | kernel exploit = host compromise | Sentry bug = userspace escape, no direct host-kernel syscall path | hardware boundary; strongest |
| Snapshot / fork | none native (CRIU non-standard) | checkpoint/restore exists in gVisor, but Modal exposes filesystem snapshots only | first-class memory+disk snapshot, pause/resume, fork |
| Cold start | fastest (process start) | near-container | ~125 ms; snapshot/restore often faster than re-running setup |
| Vendor mitigation | prebuilt local image | named Images + readiness probes (Modal) | warm pools (Daytona), snapshot-boot + pause/resume (E2B), <2 s 10 GB image + suspend/resume (Runloop) |

Sources: [firecracker-microvm.github.io](https://firecracker-microvm.github.io/), [gvisor.dev/docs](https://gvisor.dev/docs/), [docs.docker.com/engine/security](https://docs.docker.com/engine/security/), vendor docs cited above.

**Egress parity test any backend must pass** (derived from `init-firewall.sh`): (1) outbound to a non-allowlisted host fails on all protocols; (2) DNS does not leak to a non-allowlisted resolver; (3) TLS to an allowlisted host works (with the vendor CA/SNI if applicable); (4) no host credential exists in the guest (secret is an opaque ref resolved at egress); (5) no mount other than the task workspace; (6) `destroy` is guaranteed after budget/timeout/stall. Daytona's MITM CA and Modal's unrestricted-DNS/domain-fronting gaps are the two material deviations.

**Cold-start note:** for a supervised pilot with a handful of tasks the agent session dominates, so warm pools / pre-warmed images buy little and cost money. Snapshot/fork is more valuable for the runner's **stall escalation and retry** (restart from a known state) and for `harness.py orca` fan-out (fork one prepared environment into N task branches). E2B and Daytona are the only two with a genuine memory-fork story.
